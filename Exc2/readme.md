# README: Техническое задание по мониторингу системы

---

## 1. Мотивация

Мониторинг позволит получить полное представление о работе системы на основе собираемых метрик. С использованием инструментов наблюдения команда сможет быстрее определить коренные причины возникающих проблем. Анализ собранных показателей позволит выявлять узкие места, что будет способствовать принятию стратегических решений и формированию инсайдов для бизнеса. Внедрение мониторинга способствует своевременному обнаружению и устранению неполадок, что положительно скажется на пользовательском опыте.

---

## 2. Выбор подхода к мониторингу

Для реализации мониторинга в системе предлагается использовать различные подходы в зависимости от компонента:

- **Системы Shop, MES и CRM:**  
  Применяется подход «Четыре золотых сигнала». Данный метод позволяет выявлять аномалии в работе заранее и оперативно реагировать на изменения, что особенно важно для API с большим потоком клиентов.

- **Message Queue:**  
  Применяется подход «RED». Он даст представление о пропускной способности сервиса, позволит отслеживать частоту поступления заказов, наличие ошибок и время обработки запроса на взятие заказа в работу.

## 3. Метрики и контрольные показатели

Ниже приведён перечень метрик, которые будут отслеживаться в различных частях системы, а также описаны критические пороговые значения и рекомендуемые действия при их нарушении.

1. **Количество сообщений в Dead Letter Exchange (DLQ) в RabbitMQ**  
   _Описание:_ Количество сообщений, попавших в DLQ, так как они не были обработаны.  
   _Критический показатель:_ Резкое и значительное увеличение.  
   _Действия:_  
   - Проанализировать причину: неверный формат сообщений, истёкший TTL или переполненная очередь.  
   - Увеличить TTL, пересмотреть логику обработки или оптимизировать Consumer.

2. **Количество сообщений в состоянии "in flight" в RabbitMQ**  
   _Описание:_ Число сообщений, отправленных RabbitMQ, но ещё не подтверждённых Consumer.  
   _Критический показатель:_ Увеличение при нормальной работе Consumer указывает на проблемы.  
   _Действия:_  
   - Проверить производительность Consumer.  
   - Увеличить число Consumers или оптимизировать их обработку.

3. **Количество запросов (RPS) для API интернет-магазина**  
   _Описание:_ Число запросов в секунду к API интернет-магазина.  
   _Критический показатель:_ Резкий рост может указывать на DDoS-атаку.  
   _Действия:_  
   - Включить rate-limiting.  
   - Масштабировать API (добавить инстансы).

4. **Количество запросов (RPS) для CRM API**  
   _Описание:_ Число запросов в секунду к API CRM.  
   _Действия аналогичны предыдущему пункту._

5. **Количество запросов (RPS) для MES API**  
   _Описание:_ Число запросов в секунду к API MES.  
   _Действия аналогичны предыдущему пункту._

6. **Количество запросов (RPS) на одного пользователя для API интернет-магазина**  
   _Описание:_ Число запросов в секунду, отправляемых одним пользователем.  
   _Критический показатель:_ Высокая активность одного пользователя может быть подозрительной.  
   _Действия:_ Настроить rate-limiting для пользователей.

7. **Количество запросов (RPS) на одного пользователя для CRM API и MES API**  
   _Описание и действия аналогичны предыдущему пункту._

8. **Загрузка CPU для API интернет-магазина, CRM и MES**  
   _Описание:_ Процент использования процессора инстансов API.  
   _Критический показатель:_ Более 80–90% на протяжении длительного времени.  
   _Действия:_  
   - Добавить больше CPU или масштабировать инстансы горизонтально.  
   - Оптимизировать код.

9. **Использование оперативной памяти для API интернет-магазина, CRM и MES**  
   _Описание:_ Показатель использования оперативной памяти на инстансах API.  
   _Критический показатель:_ Постоянное превышение 80–90%.  
   _Действия:_  
   - Увеличить доступную память.  
   - Оптимизировать использование памяти (например, уменьшить объём кеша).

10. **Использование оперативной памяти для экземпляров баз данных интернет-магазина и MES**  
    _Описание:_ Потребление памяти базой данных.  
    _Критический показатель:_ Значения 80–90%.  
    _Действия:_  
    - Проверить настройки кэширования и оптимизировать запросы.  
    - Увеличить объём оперативной памяти.

11. **Количество соединений с экземплярами баз данных интернет-магазина и MES**  
    _Описание:_ Число активных подключений к базам данных.  
    _Критический показатель:_ Близость к максимальному лимиту (например, 1000 для PostgreSQL по умолчанию).  
    _Действия:_  
    - Настроить пул соединений (например, pgBouncer).  
    - Оптимизировать приложение для уменьшения количества соединений.

12. **Время отклика (latency) для API интернет-магазина, CRM и MES**  
    _Описание:_ Среднее время ответа API.  
    _Критический показатель:_ Значения, превышающие SLA (например, >100 мс).  
    _Действия:_  
    - Оптимизировать обработку запросов.  
    - Масштабировать API или внедрить кэширование.

13. **Объём данных в S3**  
    _Описание:_ Размер данных, хранящихся в S3.  
    _Критический показатель:_ Увеличение стоимости из-за превышения лимитов хранения.  
    _Действия:_  
    - Оптимизировать хранение данных (архивировать, удалять устаревшие файлы).

14. **Размер экземпляров баз данных интернет-магазина и MES**  
    _Описание:_ Используемое пространство базы данных.  
    _Критический показатель:_ Использование 80–90% от доступного объёма.  
    _Действия:_  
    - Увеличить объём хранилища.  
    - Архивировать или удалять старые данные.

15. **Количество HTTP 500 ошибок для API интернет-магазина, CRM и MES**  
    _Описание:_ Количество серверных ошибок.  
    _Критический показатель:_ Резкое увеличение числа ошибок.  
    _Действия:_  
    - Логировать ошибки и оперативно устранять их причины.

## 4. План действий

Ниже представлен высокоуровневый план реализации мониторинга системы:

1. **Определение метрик.**  
   - Выделить метрики производительности, бизнес-логики и ошибок (см. раздел 3).

2. **Настройка инструментов мониторинга.**  
   - Развернуть Prometheus и Grafana для сбора, хранения и визуализации метрик.

3. **Организация хранилища данных.**  
   - Создать экземпляр базы данных ClickHouse для агрегации данных мониторинга и аналитики.

4. **Настройка правил оповещения.**  
   - Определить пороговые значения для метрик (например, превышение времени отклика, рост количества ошибок) и настроить уведомления.

5. **Настройка инструментов уведомлений.**  
   - Организовать систему уведомлений (например, через email) для оперативного информирования команды о возникших инцидентах.

6. **Создание дашбордов.**  
   - Настроить Grafana для создания графиков и дашбордов, отображающих ключевые показатели производительности.

7. **Регулярный анализ.**  
   - Организовать формирование отчетов для регулярного анализа состояния и производительности системы.

8. **Интеграция с системами контейнеризации.**  
   - Убедиться, что мониторинг интегрирован с платформами (например, Kubernetes) для упрощения масштабирования и управления.

## 5. Дополнительное задание: Показатели насыщенности

Выбор показателей насыщенности основан на следующих критериях:
- **CPU и Memory Utilisation.**  
  Пороговое значение насыщенности – 80–90%. Превышение данного порога свидетельствует о том, что система приближается к максимальной загрузке.  
  _Действия:_ При достижении пороговых значений необходимо добавить вычислительные ресурсы, оптимизировать код или масштабировать систему горизонтально.

- **Количество соединений к базе данных.**  
  Порог – достижение 80–90% от максимального лимита соединений.  
  _Действия:_ Оптимизировать пул соединений и снизить нагрузку на базу данных.

- **Latency API.**  
  Если среднее время ответа превышает установленное SLA (например, >100 мс), это указывает на проблемы в производительности.  
  _Действия:_ Оптимизировать обработку запросов, масштабировать API и внедрить кэширование.

В случае превышения пороговых значений система должна инициировать автоматические оповещения, что позволит оперативно приступить к устранению причин перегрузки и, при необходимости, масштабировать ресурсы.
